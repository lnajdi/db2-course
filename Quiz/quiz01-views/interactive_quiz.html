Question 1: What is a database view?

💡 Hint: Think about whether a view stores actual data or just represents data from other tables. Consider the word "virtual" in database terminology.

📚 Detailed Explanation:

✅ Option B (Correct): A view is indeed a virtual table based on a SELECT statement. It doesn't store data physically but provides a logical representation of data from underlying tables. Views are dynamic and always reflect the current state of the base tables.
❌ Option A (Incorrect): Views are virtual, not physical. They don't store data permanently - that's what regular tables do. Views only store the query definition.
❌ Option C (Incorrect): Views are not backup copies. Backups are separate files or databases that preserve data for recovery purposes. Views are live representations of current data.
❌ Option D (Incorrect): An index is a separate database structure that speeds up data retrieval. Views are query-based virtual tables, completely different from indexes.

Question 2: Which statement about regular views is TRUE?

💡 Hint: Regular views execute their underlying query every time they're accessed. Think about what this means for data freshness and whether they need manual updates.

📚 Detailed Explanation:

✅ Option C (Correct): Regular views are "live" - they always show current data from base tables because they execute the underlying query each time they're accessed. This ensures real-time data consistency.
❌ Option A (Incorrect): Regular views don't store data physically. They're virtual and only store the query definition. Physical storage is a characteristic of materialized views or tables.
❌ Option B (Incorrect): Views can actually be slower than direct table queries because they add a layer of abstraction and may involve complex joins or calculations.
❌ Option D (Incorrect): This describes materialized views, not regular views. Regular views automatically reflect changes in underlying tables without manual refresh.

Question 3: When should you use a materialized view instead of a regular view?

💡 Hint: Consider the trade-off between query performance and data freshness. When might you accept slightly stale data for better performance?

📚 Detailed Explanation:

✅ Option C (Correct): Materialized views are perfect for complex analytical queries that are expensive to run repeatedly. They trade data freshness for performance by storing pre-computed results, making them ideal when slightly stale data is acceptable.
❌ Option A (Incorrect): Materialized views don't provide real-time data since they must be manually refreshed. If you need real-time data, use regular views instead.
❌ Option B (Incorrect): Simple and fast queries don't benefit from materialization. The overhead of maintaining a materialized view isn't worth it for queries that already run quickly.
❌ Option D (Incorrect): Materialized views actually consume MORE disk space, not less, because they store the query results physically on disk.

Question 4: What does the CHECK OPTION do in a view?

💻 Part C: Practical SQL Exercises (40 points)

Exercise 1: Basic View Creation (8 points)

Create a view called customer_contact that shows only the customer ID, first name, last name, and email from the customer table.

Sample Solution:
CREATE VIEW customer_contact AS
SELECT customer_id, first_name, last_name, email
FROM customer;

Exercise 2: Complex Join View (10 points)

Create a view named rental_details that combines information from rental, customer, film, and inventory tables to show: Rental ID, Customer's full name, Film title, Rental date, and Return date.

Sample Solution:
CREATE VIEW rental_details AS
SELECT r.rental_id, c.first_name || ' ' || c.last_name AS customer_full_name,
f.title AS film_title, r.rental_date, r.return_date
FROM rental r
JOIN customer c ON r.customer_id = c.customer_id
JOIN inventory i ON r.inventory_id = i.inventory_id
JOIN film f ON i.film_id = f.film_id;

Exercise 3: Materialized View (10 points)

Create a materialized view named film_rental_stats that shows: Film ID, Film title, Total number of rentals, Total revenue generated, and Average rental duration in days.

Sample Solution:
CREATE MATERIALIZED VIEW film_rental_stats AS
SELECT f.film_id, f.title, COUNT(r.rental_id) AS total_rentals,
COALESCE(SUM(p.amount), 0) AS total_revenue,
AVG(EXTRACT(days FROM (r.return_date - r.rental_date))) AS avg_rental_days
FROM film f
LEFT JOIN inventory i ON f.film_id = i.film_id
LEFT JOIN rental r ON i.inventory_id = r.inventory_id
LEFT JOIN payment p ON r.rental_id = p.rental_id
GROUP BY f.film_id, f.title;

Exercise 4: Security View (8 points)

Create a view called staff_public_info that shows staff information but excludes the password field. Include staff ID, first name, last name, email, and active status.

Sample Solution:
CREATE VIEW staff_public_info AS
SELECT staff_id, first_name, last_name, email, active
FROM staff;

Bonus Exercise: View with CHECK OPTION (4 points)

Create a view called active_customers_only that shows only active customers and includes the CHECK OPTION to prevent inserting inactive customers.

Sample Solution:
CREATE VIEW active_customers_only AS
SELECT customer_id, first_name, last_name, email, active
FROM customer
WHERE active = 1
WITH CHECK OPTION;
